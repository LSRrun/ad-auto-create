整体需求清晰，基于现有 React + FastAPI 架构实现难度不高，而且可以完全保留目前的规则生成模式。

## 一、需求总结

### 1. 保留原有生成模式

现有“生成广告页面”按钮和接口保持不变：

- 使用当前固定规则生成文案；
- 不需要配置大模型；
- AI 服务不可用时，原有功能仍可正常运行；
- 不改变现有图片上传、风格切换和广告预览逻辑。

也就是形成两个互不依赖的入口：

```text
生成广告页面 → 原有规则生成
AI 润色       → 大模型生成/优化文案
```

### 2. 增加“AI 润色”按钮

按照第一张图，在“生成广告页面”按钮右侧增加独立的“AI 润色”按钮。

点击后，系统会读取：

- 当前商品名称；
- 品牌和价格；
- 核心卖点；
- 当前选择的广告风格；
- 当前预览中的文案；
- 对应风格的提示词模板。

然后调用已配置的大模型，生成或润色：

- 主标题 `headline`；
- 商品描述 `description`；
- 核心卖点 `features`；
- 行动文案 `cta`；
- 可选的英文眉题 `eyebrow`。

成功后直接更新右侧广告预览，不改变商品图片、价格和当前视觉风格。

如果 AI 调用失败，保留原来的预览内容，不影响原有生成能力。

### 3. 增加模型配置入口

按照第二张图，在“商品信息”标题右侧增加“模型选择”按钮。

按钮可以显示当前状态，例如：

```text
未配置模型
DeepSeek / deepseek-chat
通义千问 / qwen-plus
自定义模型
```

点击后弹出模型配置窗口，包含：

- 服务商选择；
- 模型名称；
- API Key；
- Base URL；
- “测试连接”按钮；
- “保存配置”按钮。

配置完成后，按钮可以显示当前选择的模型，但不能显示完整 API Key。

## 二、建议交互流程

```text
点击“模型选择”
        ↓
选择服务商和模型
        ↓
填写 API Key、Base URL
        ↓
测试连接并保存
        ↓
填写商品信息、选择风格
        ↓
点击“AI 润色”
        ↓
后端组合商品信息和风格提示词
        ↓
调用大模型并要求返回结构化 JSON
        ↓
校验结果并更新右侧广告预览
```

如果用户没有配置模型就点击“AI 润色”，可以自动弹出模型配置窗口。

## 三、后端实现建议

建议新增独立的 AI 模块，不修改原有 `generator.py` 的规则模式：

```text
backend/app/
├── main.py
├── generator.py              # 保留原有规则生成
├── styles.py                 # 风格及展示文案
└── ai/
    ├── service.py            # AI 润色统一入口
    ├── providers.py          # 不同模型服务商适配
    ├── prompts.py            # 风格提示词模板
    └── schemas.py            # AI 输入和输出结构
```

新增接口可以设计为：

```text
POST /api/ai/test-connection
POST /api/ai/polish
GET  /api/ai/providers
```

AI 润色接口返回结构应尽量与现有广告数据一致：

```json
{
  "headline": "让科技，读懂每一次沐浴",
  "eyebrow": "FUTURE OF WATER",
  "description": "智能恒温系统精准控制水温……",
  "features": [
    "智能恒温控制",
    "多模式舒适出水",
    "便捷易清洁设计"
  ],
  "cta": "探索智能沐浴"
}
```

前端只需把这些字段合并到当前 `ad` 状态中。

## 四、风格提示词设计

每个风格需要增加专属 AI 提示词，例如：

```python
STYLE_PROMPTS = {
    "quiet-luxury": {
        "tone": "克制、高级、简洁，避免夸张营销词",
        "headline_length": "不超过12个中文字符"
    },
    "natural-spa": {
        "tone": "自然、舒缓、具有生活方式感",
        "headline_length": "不超过14个中文字符"
    },
    "midnight-tech": {
        "tone": "现代、科技、专业，突出智能体验",
        "headline_length": "不超过14个中文字符"
    }
}
```

提示词还需要明确要求模型：

- 不能虚构用户没有提供的产品参数；
- 不擅自修改品牌和价格；
- 卖点最多保留 3 个；
- 必须返回 JSON；
- 控制标题和描述长度；
- 文案应符合当前广告画布的空间限制。

## 五、多模型接入的可行性

可行性较高，但“各个大模型”建议分两类处理。

### OpenAI 兼容模型

很多模型服务支持类似 OpenAI 的接口格式，可以通过统一配置接入：

- DeepSeek；
- 通义千问兼容接口；
- 智谱兼容接口；
- Moonshot/Kimi；
- OpenAI；
- 本地 Ollama 或其他兼容服务；
- 用户自定义 Base URL。

这一类可以共用一个适配器，开发成本较低。

### 非兼容模型

Anthropic Claude、Google Gemini 等服务的原生请求结构不同，需要单独编写适配器。

因此第一版建议优先支持：

1. DeepSeek；
2. 通义千问；
3. OpenAI；
4. 自定义 OpenAI 兼容接口。

后续再增加 Claude、Gemini 等专属适配器。

## 六、API Key 安全策略

API Key 不建议直接写入项目代码或 `.env` 后提交，也不建议长期明文存放在浏览器 `localStorage`。

一期 AI 模块可以采用：

- API Key 只保存在当前页面内存；
- 刷新页面后需要重新填写；
- 每次请求通过 HTTPS 发给后端；
- 后端不记录、不打印 API Key；
- 错误日志中隐藏敏感请求头。

未来增加用户系统后，再实现：

- 服务端加密存储；
- 每个用户独立配置；
- 返回前端时只显示掩码；
- 支持修改和删除配置。

本地开发阶段使用内存配置足够简单，也最符合“不影响原有模式”的要求。

## 七、需要特别处理的问题

- AI 请求可能持续几秒，需要单独的加载状态；
- AI 润色按钮必须防止连续重复点击；
- 调用失败不能清空当前广告文案；
- 模型返回的 JSON 可能不标准，需要后端校验和容错；
- 切换风格后再次润色，必须使用最新风格模板；
- AI 润色结果不能被原有规则生成无意覆盖；
- API Key 不能出现在日志、错误信息或接口响应中；
- Base URL 需要做格式检查，并考虑服务端请求伪造风险。

## 八、实现结论

这个功能非常适合在现有架构上增量实现，不需要重构项目。

推荐按照以下顺序开发：

```text
模型配置弹窗
    ↓
OpenAI 兼容模型适配器
    ↓
风格提示词模板
    ↓
AI 润色接口
    ↓
前端 AI 润色按钮
    ↓
连接测试、错误处理和安全限制
```

第一版先实现“OpenAI 兼容接口 + 页面内临时保存配置”，代码量和复杂度都比较可控；原有规则生成保持独立，即使没有 API Key 或模型服务发生故障，当前广告生成功能也不会受到影响。
